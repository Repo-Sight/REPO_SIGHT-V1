How to measure code quality

← Back to Learn

Code quality cannot be captured in one number, but parts of it can be measured, and the parts that can be measured are worth tracking. This guide explains what "quality" is made of, which metrics are objective and which are only proxies, and walks through a real project's score step by step so you can see exactly how a number like 78 is produced. It also covers the ways measurement goes wrong, because a metric you optimise blindly stops being useful.

What "quality" means

People use the word for several different things, and mixing them up leads to arguments. A useful split:

  • Maintainability: how easy the code is to read, change and extend. This is what most static metrics measure.
  • Reliability: whether it behaves correctly under real conditions. Mostly measured by tests and production monitoring, not by reading source.
  • Security: whether it resists misuse. Partly visible as risky patterns in the code.
  • Performance: whether it is fast and frugal enough. Needs profiling, not static reading.

A static analyser, REPO-SIGHT included, is strongest on maintainability and on the security patterns that have a recognisable shape. It does not measure reliability or performance, and it says nothing about whether the code does the right thing.

Metrics you can compute from the source

These five are the inputs to REPO-SIGHT's health score. Each is a plain fact about the text of the code, so it can be recomputed exactly:

  • Complexity density (35% of the score): total cyclomatic complexity divided by lines of code. Full marks at 0.15 or below, zero at 0.50.
  • Average function length (25%): full marks at 15 lines or fewer, zero at 60 or more.
  • Comment density (20%): comment lines per line of code. Full marks at 0.20, zero at 0.02.
  • TODO density (10%): TODO and FIXME markers per line of code. Full marks at 0.01 or below, zero at 0.05.
  • Maximum nesting depth (10%): the deepest block in the project. Full marks at 3 levels, zero at 8. See maximum nesting depth.

Each component is scaled from 0 to 100 between its "good" and "bad" reference points, then the five are combined using the weights above. A score of 90 or more is an A, 80 a B, 70 a C and 60 a D.

A worked example: scoring Flask by hand

The best way to trust a score is to recompute it. Here are the figures from our October 2026 scan of Flask, the Python web framework:

  • 13,989 lines of code, 781 comment lines, 1,462 functions
  • Average function length 8.6 lines
  • Cyclomatic total 817, so complexity density = 817 ÷ 13,989 = 0.058
  • Maximum nesting depth 6
  • 0 TODO or FIXME markers

Now score each component:

  1. Complexity density 0.058 is under 0.15, so it earns 100.
  2. Function length 8.6 is under 15, so 100.
  3. Comment density is 781 ÷ 13,989 = 0.056. That sits between 0.02 (zero) and 0.20 (full), at (0.056 − 0.02) ÷ 0.18 = about 20.
  4. TODO density is 0, so 100.
  5. Nesting depth 6 sits between 3 (full) and 8 (zero), at (8 − 6) ÷ 5 = 40.

Weight them: 0.35 × 100 + 0.25 × 100 + 0.20 × 20 + 0.10 × 100 + 0.10 × 40 = 35 + 25 + 4 + 10 + 4 = 78. That is a C, and it matches the score REPO-SIGHT reported.

What the example teaches

First, a C here does not mean the code is poor. Flask scores full marks on three of five components and loses its points in two places: comments and nesting. The comment loss is mostly a counting convention. REPO-SIGHT counts only # comments in Python, and Flask documents itself heavily in docstrings, which do not count. We tested this on a small file: a function with a three-line docstring and one # comment reports one comment line.

Second, you can see exactly which levers move the score. Cutting maximum nesting from 6 to 3 would lift the nesting component from 40 to 100, which adds 6 points and moves Flask from 78 to 84, a B. Reaching 0.20 comment density would need about 2,000 more # comment lines for +16 points, which is the wrong goal because padding code with comments does nothing for readers. Knowing the formula lets you spot which improvements are real and which are gaming.

Third, compare like with like. Across the 53 open-source projects we scanned, Java projects averaged 90 and Python projects 74, almost entirely because of how comments are counted. Ways measurement goes wrong

  • Optimising the number, not the code. When a measure becomes a target it stops being a good measure. Adding comments to raise a score, or splitting a function in the middle of a thought to reduce its length, improves the metric and worsens the code.
  • Reading averages and ignoring outliers. A healthy average hides the one 400-line function that everyone is afraid of. Look at the worst files and functions, not only the project total.
  • Ignoring where the findings are. About 58% of the findings in our 53-project scan were in tests, docs, examples or bundled code. A number that mixes them with production code overstates the problem. See where static analysis findings actually live.
  • Treating a clean report as proof. It means none of the checks the tool knows about fired. It says nothing about tests, design or whether the feature works.
  • Comparing across languages. Conventions differ. Compare a project with others in the same language, or better, with its own past.

A practical way to measure your own code

  1. Take a baseline. Scan the whole repository once and save the result. The number matters less than having a starting point.
  2. Pick two or three metrics that fit your problem. If reviews drag on, watch function length and nesting. If bugs cluster in error handling, watch the empty-catch and bare-except findings.
  3. Fix the worst offenders first. Start from the ranked "fix these first" list, not from the longest list of low-severity items.
  4. Rescan and compare. The change since the last scan tells you whether your effort is working. A rising trend is a better warning than one high reading.
  5. Add what a static tool cannot see. Track test coverage, defects found in production and the time changes take, alongside the static numbers.

Frequently asked questions

What is a good code health score?

90 or above is an A, but treat the grade as a conversation starter. In our data, only 15 of 53 respected projects earned an A, and many excellent projects scored a B or C.

Is the score reproducible?

Yes. It is computed from published constants, so you can recompute it from the five inputs, as we did for Flask. We recomputed every project's score in our 53-project data file and each matched to within a tenth of a point.

Which single metric matters most?

There is no single answer. If you must pick one place to look, find your functions with the highest complexity and deepest nesting, because they combine the two most common sources of hard-to-follow code.
