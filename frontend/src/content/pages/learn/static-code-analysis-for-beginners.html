Static code analysis for beginners

← Back to Learn

If you have never run a static analysis tool, the output can look like a wall of warnings. This guide walks through a first scan from start to finish: what to scan, what the results mean, which ones to act on, and how to check that your fix worked. You need no setup, no signup and no knowledge of the tool. By the end you will have read a real report and know what to do with the next one.

What static analysis does, in one paragraph

A static analysis tool reads your source code without running it and points at patterns that are risky, confusing or hard to maintain. Think of it as an automated first reviewer that never gets tired and checks every line for the same mechanical mistakes. It does not replace testing or a human reviewer, and it can be wrong. If you want the full background first, read what is static analysis?. Otherwise, jump in.

Step 1: Look at a demo report first

On the REPO-SIGHT home page, the Try a demo report button opens a pre-analysed example, so you can see what a finished report looks like before you point the tool at your own code. Spend two minutes with it. Find the overall score and grade, the list headed "Fix these first", and the tabs along the top. You will recognise all of them in your own scan.

Step 2: Choose what to scan

There are two ways in, and both are free, need no account and never run your code:

  • GitHub repo. Paste the address of a public repository, for example https://github.com/owner/repo, and press Analyze now. Good for a whole project.
  • Paste or upload a file. Give the file a name such as app.py, paste the code or choose a file, and press Analyze now. Good for a first try or a single script.

REPO-SIGHT supports C++, Python, Java, TypeScript, JavaScript and C#. For a first scan, a small project you wrote yourself is best, because you will understand the findings. Avoid starting with a giant framework: it will produce thousands of results and teach you little.

Step 3: A worked example on one small file

Here is a short Python file with a few deliberate mistakes. If you paste it in as app.py, you will get the findings listed below it. We ran this exact file through REPO-SIGHT.

import os, subprocess, pickle

API_KEY = "sk_live_51HxQ2eLkd93jfPzR8vTn40aB"

def run_expression(user_input):
    return eval(user_input)

def ping(host):
    os.system("ping -c 1 " + host)

def load_session(f):
    return pickle.load(f)

# TODO fix this later
def x():
    pass

The tool reports five findings. Here is how to read each one:

  • py-sec-hardcoded-secret, line 3. A password-like string is written directly in the code. Anyone who can see the repository can see it, and it stays in the history even if you delete the line. Move it to an environment variable. If it was a real key, replace it.
  • py-sec-eval-exec, line 6. eval runs a string as code. If any part of the string comes from a user, they can run their own code on your machine. Use ast.literal_eval for plain data.
  • py-sec-os-system, line 9. The command is built by joining text, so a "host" value could contain extra commands. Pass the arguments as a list to subprocess.run.
  • py-sec-pickle-load, line 12. Loading a pickle file can execute code hidden inside it. Use JSON for data you receive.
  • py-todo-without-ticket, line 14. A note to yourself with no issue number attached. Add one, such as TODO(#142), or delete the note.

Notice the tone of the messages: each one says what the code does and what to check. The tool is not telling you the code is broken, only that these are the spots worth a human look. That is the right way to treat every finding you will ever see.

Step 4: Read a full report

For a repository, the report opens on the Overview tab. These are the pieces worth knowing:

  • Score and grade. A single number out of 100 and a letter, from five measurements: complexity, function length, comments, TODO markers and nesting. The Scoring tab shows each component, so you can see why you got the grade. See reading a code health score.
  • Fix these first. The most important findings, ranked by severity and confidence, so you do not have to sort a long list yourself.
  • Fix now. A card that appears above the rest when there are high-severity, high-confidence problems such as an empty error handler that hides failures. If you see it, start there.
  • Language mix. The share of each language in the project, useful when a repository contains, say, a Java backend and some Python scripts.
  • Tabs. Languages, Files, Findings, Security, Scoring and Duplication each show one slice in more detail. The Files tab tells you which files hold the most trouble, which is usually where to begin.

Step 5: Fix one thing and scan again

Do not try to clear everything. Pick the top item, fix it, and scan again. Here is the earlier file after fixing all five findings:

import ast, os, subprocess, json

API_KEY = os.environ["API_KEY"]

def run_expression(user_input):
    return ast.literal_eval(user_input)

def ping(host):
    subprocess.run(["ping", "-c", "1", host], check=True)

def load_session(f):
    return json.load(f)

# TODO(#142): fix this later
def x():
    pass

Run it through REPO-SIGHT and it reports no findings. This before-and-after loop is the real habit to build: scan, fix the most important thing, scan again and compare. The difference between two scans is how you know you made progress, and it is far more motivating than a single number.

Common beginner mistakes

  • Chasing a perfect score. A 100 is not the goal. Only 15 of the 53 respected open-source projects we scanned earned an A, and several widely admired ones scored a C. Use the score to decide where to look, not to judge yourself.
  • Fixing in the order of the list. A tool can show a long list of low-priority style issues before the one serious problem. Start with the ranked items.
  • Ignoring the file path. A finding in a test or an example file matters much less than the same finding in code that ships. About 58% of findings in our scan sat in non-production paths. See where static analysis findings actually live.
  • Believing every warning. Tools produce false positives. A bare except: that cleans up and re-raises is fine. If you read the code and it is correct, move on.
  • Believing a clean report means safe code. It means the checks the tool knows did not fire. You still need tests and review.

A tiny glossary

  • Finding: one place where a rule matched, with a file, a line and a message.
  • Rule: one check, such as py-bare-except. The prefix shows the language.
  • Severity: how serious a finding is: critical, high, medium or low.
  • Confidence: how likely the tool is to be right about this finding.
  • Cyclomatic complexity: how many different paths run through a function.
  • Nesting depth: how many blocks sit inside one another.

Frequently asked questions

Do I have to sign up?

No. Scanning is free and needs no account. Your code is read, never executed.

Will it work if my code does not compile?

Yes. It reads the source text directly, so unfinished or broken code can still be analysed.

How long does a scan take?

A single file takes moments. A repository takes longer in proportion to its size, and very large ones may hit time limits.

What should I learn next?

Read the language guide for your stack: Python, Java or C++, each of which shows before-and-after fixes for the findings you are most likely to meet.

Run your first scan

Open the analyzer, choose a file or a public repository, and press Analyze now. Start with something small that you wrote, and fix the top finding.
