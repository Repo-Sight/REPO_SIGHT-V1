How to read a code health score

← Back to Learn

A single letter grade is convenient, but it is only useful if you know what is measured underneath it. This guide shows exactly how REPO-SIGHT's health score is calculated, works through two real projects line by line, and lists the three things worth knowing before you trust any score — ours included.

The five components

Each component is scored from 0 to 100 by comparing your project's value against two reference points. At or better than the "good" reference it scores 100. At or worse than the "bad" reference it scores 0. In between, the score slides in a straight line. The five scores are then combined by weight:

  • Complexity density — 35%. Total cyclomatic complexity divided by lines of code. Full marks at 0.15 or lower, zero at 0.50 or higher.
  • Average function length — 25%. Full marks at 15 lines or fewer, zero at 60 or more.
  • Comment coverage — 20%. Comment lines divided by code lines. Full marks at 20% or more, zero at 2% or less.
  • TODO density — 10%. TODO/FIXME-style markers divided by code lines. Full marks at 1% or lower, zero at 5% or higher.
  • Max nesting depth — 10%. The deepest block nesting found anywhere in the project. Full marks at depth 3 or less, zero at depth 8 or more. See nesting depth explained.

The grade thresholds

The five weighted scores sum to one overall number out of 100, which maps to a letter:

  • A — 90 and above
  • B — 80 to 89
  • C — 70 to 79
  • D — 60 to 69
  • F — below 60

Worked example: a project that scores an A

We scanned Google's Gson library (Java, commit e2292f9) on 14 October 2026. Its five component scores were 100 for complexity density, 100 for function length, 100 for comment coverage, 100 for TODO density — and 0 for nesting depth, because somewhere in the project a block nests 8 levels deep. The sum:

0.35 × 100 + 0.25 × 100 + 0.20 × 100 + 0.10 × 100 + 0.10 × 0 = 90

That lands exactly on the A threshold. One deep spot cost the whole 10 points of the nesting component.

Worked example: a well-regarded project that scores a C

Flask (Python, commit d086db8) scanned the same day gets 100 for complexity density, 100 for function length and 100 for TODO density. Its two weak components are comment coverage and nesting:

  • Flask has 781 comment lines against 13,989 code lines, a comment density of about 5.6%. On the scale from 2% (zero) to 20% (full), that is a score of 19.9.
  • Its deepest nesting is 6, which on the scale from 8 (zero) to 3 (full) scores 40.
0.35 × 100 + 0.25 × 100 + 0.20 × 19.9 + 0.10 × 100 + 0.10 × 40 = 77.98  → C

A useful way to read this: instead of adding up what you earned, count what you lost. Comment coverage cost Flask 0.20 × (100 − 19.9) = 16 points, and nesting cost 6. Everything else is full marks, so 100 − 22 = 78.

There is an important detail behind that comment score. REPO-SIGHT counts comment lines, and a Python docstring is technically a string, so its lines are counted as code rather than comments. We confirmed this by scanning a function with a multi-line docstring: only its # comment was counted. Flask documents its code heavily this way — 257 of the 466 modules, classes and functions under src/ carry a docstring — so a score of 19.9 understates how well documented it is. The grade is accurate to how the score is defined, but it is not a verdict on Flask's documentation.

Three things to know before you trust a score

  • Everything scanned counts, including tests and examples. A default scan reads every supported file in the repository. Across the 19 open-source projects we scanned, roughly two-thirds of rule findings sat in paths that look like tests, docs or examples (a path-name heuristic, so approximate). If a score looks harsh, check how much of it comes from non-production code.
  • The nesting score reflects a single worst spot. It uses the project-wide maximum, so one deeply nested function — or one generated file — can dominate it. In the Fastify repository the deepest block we found was in a generated validator file, at depth 41.
  • Complexity density rarely separates projects. It carries the largest weight, but to lose points a project needs a density above 0.15. Across the 19 projects we scanned, densities ranged from 0.038 to 0.125, so every one of them scored 100 on that component. In practice, the lower components — function length, comments and nesting — are what moved the grades.

What to fix first on a low grade

Work out where the points went rather than guessing. For each component, points lost equal its weight times (100 minus its score). The component with the biggest loss is the highest-leverage fix.

  • If function length is the biggest loss, sort functions by length and split the top few. This often drops complexity and nesting at the same time.
  • If nesting is the biggest loss, find the single deepest function and flatten it with early returns. One fix can recover up to 10 points.
  • If comment coverage is the biggest loss, add comments where the reasoning is not obvious from the code. Padding comments to move the number helps nobody; the component rewards a healthy level, not a maximum.
  • If complexity density is the biggest loss, look at the most branchy functions first.

Frequently asked questions

Does a low grade mean the code is bad?

No. A score is a starting point for triage. A C-graded project can be well designed with a couple of legitimately complex algorithms, and an A-graded one can still have logic bugs that metrics cannot see.

Why did my small project's grade change so much after a small edit?

Small codebases move quickly. Average function length is an average, and nesting depth is a maximum, so adding or restructuring one function can shift both noticeably.

Which languages does the score cover?

C++, Python, Java, TypeScript, JavaScript and C#, using the same weights and reference points for each.
