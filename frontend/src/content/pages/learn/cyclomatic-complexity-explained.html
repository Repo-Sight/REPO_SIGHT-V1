Cyclomatic complexity, explained

← Back to Learn

Cyclomatic complexity is a count of the independent paths through a piece of code. Thomas McCabe introduced it in 1976 to put a number on something programmers already sensed: some functions are easy to reason about, and some are a tangle. This guide covers exactly what gets counted, walks through a function by hand, shows what we measured on real open-source projects, and explains where the number misleads.

What actually gets counted

A function starts at a baseline of 1 — one straight-line path with no branching. From there the count goes up by one at every point where execution can fork: an if or elif, a loop (for, while), a case in a switch or match, a catch or except block, a ternary ?:, and short-circuit boolean operators like &&, ||, and and or. Each one is a decision point — a place where execution can take one of at least two routes.

Two things are deliberately not counted. A bare else adds nothing, because it is just the other side of a decision already counted at its if. And a try adds nothing by itself; the branch comes from the except or catch that handles a failure. The result approximates the number of distinct paths a test suite would need to exercise every branch at least once.

A worked example, by hand

Here is a small Python function that prices shipping for an order:

def ship_cost(order, express, member):
    if order is None:                              # +1
        return 0
    total = 0
    for item in order.items:                       # +1
        if item.weight > 20 and not item.digital:  # +1 (if), +1 (and)
            total += 12
        elif item.weight > 5 or express:           # +1 (elif), +1 (or)
            total += 7
        else:
            total += 3
    if member:                                     # +1
        total = total * 0.9
    return total

Count the decision points: one if, one for, one if with an and, one elif with an or, and a final if. That is 7 decision points, plus the baseline of 1, for a complexity of 8. The else and the plain return statements add nothing. We ran this exact function through REPO-SIGHT and it reports 8.

Two numbers, not one

REPO-SIGHT reports complexity at two levels, and it helps to know which is which.

  • Per file. Each source file starts at 1 and gains one for every decision point anywhere in it. These per-file counts add up to the project-wide figure, and that figure divided by code lines is the "complexity density" that feeds the health score.
  • Per function. A separate check counts decision points inside each function and raises a -complex-function finding when a function goes above 10. The finding names the function and its count, for example "has cyclomatic complexity 16 (limit 10)".

The per-function number is the one to act on, because a limit of 10 applies to a single function rather than a whole file. The per-file figure mostly tells you how branchy a codebase is overall.

What we measured on real projects

To see what the limit of 10 looks like in practice, we scanned six well-known open-source projects on 14 October 2026 and counted how many functions went over it. These are whole-repository scans, so tests and examples are included.

  • Flask (Python): 5 of 1,462 functions over the limit — 0.3%.
  • Requests (Python): 5 of 711 — 0.7%.
  • Django (Python): 348 of 33,201 — 1.0%.
  • Gson (Java): 52 of 3,446 — 1.5%.
  • Jackson Core (Java): 191 of 5,779 — 3.3%.
  • Guava (Java): 261 of 56,738 — 0.5%.

The pattern is that mature, widely reviewed projects keep the overwhelming majority of functions under 10, and the few that exceed it tend to be the ones with real branching to do: Flask's most complex function, Blueprint.register, scores 23 because it resolves name conflicts, sets up the static folder and recurses into nested blueprints. High complexity there is not an accident, but it is exactly the function a new contributor will find hardest to change safely.

One caveat on these figures: REPO-SIGHT counts decision points by reading tokens rather than building a full syntax tree. We cross-checked it against a syntax-tree count on Flask and Requests. The two agreed exactly on several of the most complex functions, but REPO-SIGHT undercounted a few others, so treat its numbers as a reliable ranking of where to look rather than an exact audit.

Why it correlates with bugs — and why that is partly size

High complexity usually means a function is doing more than one job, is hard to hold in your head, and needs many test cases to cover. Studies going back to McCabe's work have found a link between high complexity and defects. Later research is more cautious: much of that link shrinks once you account for function length, because long functions tend to have more branches. Complexity is best read as a proxy for tangled logic, not as a cause of bugs on its own.

Counting differs between tools

Tools disagree on details: whether every case counts or the whole switch counts once, whether boolean operators count, whether comprehensions and ternaries count. A function that scores 12 in one tool may score 10 or 15 in another. Compare numbers within one tool over time, not across tools.

Bringing it down

Refactoring does not make decision points disappear — it moves them somewhere easier to read. Take the function above and pull the per-item pricing into a helper:

def item_cost(item, express):
    if item.weight > 20 and not item.digital:
        return 12
    elif item.weight > 5 or express:
        return 7
    return 3


def ship_cost(order, express, member):
    if order is None:
        return 0
    total = 0
    for item in order.items:
        total += item_cost(item, express)
    if member:
        total = total * 0.9
    return total

item_cost now scores 5 and ship_cost scores 4, down from 8 for the original. The file as a whole still reports 8, because the same seven decision points exist. That is the point: the worst single function dropped from 8 to 5, which is what makes the code easier to test, one function at a time.

  • Extract sub-functions. Isolate a branchy block behind a well-named function, as above.
  • Use early returns. Guard clauses reduce nesting even when the branch count stays the same. See nesting depth for why that matters.
  • Replace long if/elif or switch chains with a lookup. A dictionary from condition to behaviour swaps many branches for one lookup.
  • Split functions that do two things. Validating, transforming and reporting in one function is a common source of 15+ scores.

Frequently asked questions

What is a good cyclomatic complexity score?

For a single function, 1–10 is comfortable, 11–20 deserves a second look, and above that is a strong refactoring candidate. REPO-SIGHT flags functions above 10.

Does an else add to the count?

No. The decision was already counted at the if. An else if or elif does add one, because it introduces a new condition.

Is high complexity always bad?

No. A parser or a state machine can be legitimately branchy. What matters is whether the complexity is isolated, tested and understood. A function that is a clear outlier among its neighbours is usually the one to look at first.

How REPO-SIGHT reports it

REPO-SIGHT reads each C++, Python, Java, TypeScript, JavaScript or C# file, increments a counter at every branch point, and reports both the per-file totals and any function above the limit of 10. Complexity density carries a 35% weight in the health score. Try the complexity checker or run it on a repo to see your own numbers.
