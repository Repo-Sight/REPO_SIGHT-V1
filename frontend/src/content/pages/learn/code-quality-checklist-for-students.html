Code quality checklist for students

← Back to Learn

A class project graded on whether it runs is a different bar from a GitHub repository you link on your resume. This checklist is for the second case, the one a recruiter, interviewer or open-source maintainer might actually open. It is split into things you can check by eye, things a scan can check for you, and a worked example with real before-and-after output, including one result that surprised us and that you should know about before you start chasing a grade.

Part 1: the repository itself

  • Does it have a README? One paragraph on what the project does, how to install it and how to run it. An empty or default README is one of the quickest ways to look unfinished.
  • Is there a LICENSE file? It does not need to be complicated. MIT or Apache 2.0 is fine. A public repository with no licence gives other people no clear terms for reusing it.
  • Is there a .gitignore? A repository with node_modules/, a virtual environment or compiled binaries committed signals unfamiliarity with basic tooling.
  • Are commit messages readable? A history of “fix”, “fix2” and “asdf” is minor individually and a pattern collectively.
  • Is there at least one test? It does not need full coverage. One test file shows you know testing exists as a practice.
  • Can a stranger run it? Follow your own README on a clean checkout, ideally on another machine. Missing steps show up immediately.

Part 2: secrets and safety

This is the section where a mistake costs the most, so check it first.

  • No keys, tokens or passwords in the code. Read configuration from environment variables and keep a .env.example with dummy values. REPO-SIGHT flags hardcoded credentials and provider-style tokens, for example py-sec-hardcoded-secret and py-sec-secret-token in Python and the matching rules in each other language.
  • If a real key was ever committed, revoke it. Deleting the line in a later commit does not remove it from the repository history, where anyone can still read it. Treat the key as leaked, create a new one and use that.
  • Avoid the obviously dangerous calls unless you truly need them: eval, shell commands built from user input, SQL built by string concatenation, and disabled certificate checks. The scanner has a rule for each.

Part 3: the code

  • Does the longest function fit on one screen? REPO-SIGHT reports a project’s longest function by name and length. A 300-line function is a concrete number you can look up, not a vague impression. Anything over 100 lines is flagged (py-long-function, java-long-method and equivalents).
  • Are there any bare except: or empty catch blocks? They hide failures, and most CS courses teach them as an anti-pattern, so an interviewer skimming your code will notice. They are flagged as py-bare-except, java-empty-catch-block and so on.
  • Is nesting reasonable? More than about four levels deep is hard to read. See maximum nesting depth for how to flatten it with early returns.
  • Are there leftover TODOs? A handful with a ticket number is normal. Dozens of “TODO: fix this” comments look abandoned.
  • Has tutorial boilerplate been removed? Leftover comments, variable names and sample code from the tutorial you followed stand out.
  • Is everything in one 1,000-line file? Split logic, input and output, and configuration.

A worked example

We wrote a deliberately typical student file, about 17 lines of Python that call a web API, and ran it through REPO-SIGHT. It contained a hardcoded key (a dummy value starting sk-ant-), a hardcoded password, a TODO with no ticket, a bare except:, a mutable default argument, and a loop with three nested if statements. The scan reported five findings:

  • py-sec-secret-token, line 2 (warning)
  • py-sec-hardcoded-secret, line 3 (warning)
  • py-todo-without-ticket, line 6 (info)
  • py-bare-except, line 10 (warning)
  • py-mutable-default-arg, line 13 (warning)

The maximum nesting depth was 5 and the grade was F at a score of 50. We then fixed it the way you would: the key now comes from os.environ, the except names requests.RequestException, the default argument is None, the TODO references a ticket, a request timeout was added, and the nested conditions became a single guard clause with continue.

def total(items=None):
    # TODO #12: handle discounts
    s = 0
    for i in items or []:
        if not (i and i.price and i.qty):
            continue
        s += i.price * i.qty
    return s

The rescan reported zero findings and a nesting depth of 3. The score, however, went from 50.0 to 50.1, and the grade stayed an F.

Why the grade did not move, and what to do about it

This is the most useful lesson on the page. On a file of under twenty lines, two of the five score components dominate. Complexity density is total cyclomatic complexity divided by lines of code, and a few branches in a very short file produce a high ratio. Comment density is also low, because the file has one comment. Neither improved by removing the findings, so the number stayed put. The health score was designed for whole projects, where the ratios average out. On a tiny file it is noisy.

So read the checklist in this order: findings first, grade second. The five findings above are real problems that a person reading your code would notice, and removing them is what makes the repository look better. A grade on a 20-line file tells you very little. A grade on a full project is more meaningful, and even there it is a rough guide. In our study of 53 respected open-source projects, only 15 earned an A, and the most common grade was a C. A B on your project is a good result.

If you write Python, one more thing to know: REPO-SIGHT counts only # comments in its comment score, not docstrings. A well-documented Python project can still score low on that component. We explain this, with measurements, in what code health grades look like across 53 projects.

A five-minute pre-submission routine

  1. Read the README as if you had never seen the project. Does it say what to do?
  2. Run the repository through REPO-SIGHT. No signup is needed for a public repository. Look at the security findings first, then the longest function.
  3. Fix the worst one or two things it flags. You are not after a perfect score. You are removing obvious, fixable outliers from a repository someone is about to open.
  4. Rescan and confirm the findings you fixed are gone. Do not chase the grade past that point. A clean, honest B is more convincing than a suspiciously perfect A on something that was never really tested.

Frequently asked questions

Do recruiters actually run code analysis tools on student repositories?

We do not know of any reliable data on this, and we would not claim it. What a reader can see without any tool is the README, the file layout and whichever file they click first, and the checklist above is about making sure those hold up.

Should I add tests just to look good?

Add tests that check something real, even if there are only a few. A test file with nothing meaningful in it is easy to spot and looks worse than none.

What grade should I aim for?

Aim for no security findings and no obvious outliers, not for a letter. For a full project, a B or a C in a language that scores low on comments is a normal, respectable result.

Why this matters more than it seems

A reader who opens your linked repository will form an impression from the README, the structure and one or two files. They will not read everything. A short pass before you submit is cheap insurance against that impression being the wrong one. For more on the habits behind it, see how to measure code quality and how to improve Python code quality.
