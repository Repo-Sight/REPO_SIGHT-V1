What is code complexity?

← Back to Learn

Code complexity is a measure of how hard a piece of code is to understand, change and test. It is not one number. Different measures capture different kinds of difficulty: how many paths a function has, how deeply its blocks are nested, how long it is, how many other things it depends on. This guide separates those measures, shows each on a small example, and uses data from 53 open-source projects to show what typical numbers look like.

Why complexity matters

Nobody reads code to admire it. They read it to change it, and every extra branch is something the reader must hold in mind while doing so. Complex code is slower to review, easier to break and harder to cover with tests, because each independent path needs its own case. Complexity also hides bugs: the more combinations of conditions a function has, the more likely one of them was never thought about.

None of that makes complexity bad in itself. A tax calculation or a parser genuinely has many cases. The goal is to know where the complexity lives, keep it contained, and not let it spread into code that should be simple.

Four things people mean by "complexity"

1. Cyclomatic complexity: how many paths

Cyclomatic complexity counts the decision points in a function: each if, loop, case, catch and short-circuit operator adds one to a baseline of 1. It approximates how many test cases are needed to exercise every branch. Our cyclomatic complexity guide counts one function by hand.

2. Nesting depth: how deep

Nesting depth is how many blocks sit inside one another. A loop containing an if containing another loop is three levels deep, and the reader must remember all three conditions at once. Here is a function that is only 8 lines long but deep:

def process(orders):
    for o in orders:
        if o.paid:
            for line in o.lines:
                if line.stock:
                    for w in line.warehouses:
                        if w.open:
                            ship(w, line)

REPO-SIGHT reports a maximum nesting of 7 for this file and raises py-deep-nesting, because the limit is 6. Its cyclomatic complexity is also 7, so both measures agree here. They do not always. A flat chain of elif branches can have high complexity and shallow nesting, and the reverse is possible too. See maximum nesting depth, explained.

3. Function length: how much

Length is the simplest measure and often the most revealing. A function that does not fit on one screen forces the reader to scroll and lose context. REPO-SIGHT flags functions over 100 lines (py-long-function, java-long-method and the equivalents), and the health score uses the average function length for the project, rewarding an average near 15 lines and giving nothing for 60 or more.

4. Coupling: how connected

Coupling is how much a piece of code depends on other pieces. A function can be short and simple but impossible to change safely because ten other modules call it. Coupling is real and important, but it needs whole-program information to measure well, and REPO-SIGHT's headline metrics do not try to capture all of it. Keep that in mind: a low complexity score is not the same as a well-designed system.

A related idea: cognitive complexity

Cyclomatic complexity treats a flat list of ten case branches the same as ten nested if statements, although the second is far harder to read. Cognitive complexity was designed to fix this by adding extra weight for nesting. REPO-SIGHT does not compute a cognitive score; it reports cyclomatic complexity and nesting depth as separate numbers, which together approximate the same intuition. If a function scores high on both, it is the one to look at first.

What typical numbers look like

Abstract thresholds are hard to judge without a reference, so here is what we measured. REPO-SIGHT scores each project's complexity density: total cyclomatic complexity divided by lines of code. Across 53 well-regarded open-source projects:

  • The median complexity density is 0.080, or about 8 decision points per 100 lines of code.
  • The range runs from 0.038 (FastAPI) to 0.225 (Retrofit).
  • Only one of the 53 is above 0.15, the point at which the health score starts to deduct anything for it.
  • The median average function length is 10.8 lines, and 13 of the 53 average more than 15.
  • The median maximum nesting depth is 10. Almost every large project has at least one deeply nested block, and 48 of the 53 reach 8 or more.

Two lessons follow. First, well-maintained projects keep complexity low on average, which is why density costs almost nothing in their scores. Second, a project-wide average hides the outliers, and outliers are where problems live. The single deepest block in a large project says little about the rest of its code. That is why REPO-SIGHT also flags individual functions rather than only reporting an average. For the long-function side of this, see long and complex functions in 14 C++ projects.

Reading a complexity number sensibly

  • Compare like with like. A parser, a compiler pass and a CRUD handler have different natural complexity. Compare a function with its neighbours.
  • Look at the worst functions, not the average. One 25-branch function matters more than a hundred 2-branch ones.
  • Check the path. Complexity in a test or an example matters less than the same number in code that ships.
  • Watch the trend. A number that rises with every release is a better warning than a single high reading.

How to reduce it

Reducing complexity usually means moving it rather than deleting it. Split a function that does two jobs into two functions. Replace a long if/elif chain with a lookup table. Use early returns to flatten nesting. Each change makes one function easier to read, even when the total number of decisions in the file stays the same. Frequently asked questions

Is code complexity the same as code quality?

No. Complexity is one input. Good code can be complex because the problem is, and simple code can be wrong or badly designed. Use complexity to decide where to look, not to give a verdict.

What is a good complexity score?

For a single function, 1 to 10 is comfortable. For a project, a complexity density below about 0.15 is considered healthy by REPO-SIGHT's score.

Which complexity measure should I track first?

Start with cyclomatic complexity per function and maximum nesting depth. Together they catch most of the code that is hard to follow.

Measure your own code

Try the code complexity checker or scan a repository to see the complexity, nesting and length of every file, and which functions cross the limits.
