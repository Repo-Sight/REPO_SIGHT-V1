What is static analysis?

← Back to Learn

Static analysis is the practice of examining source code without running it. A tool reads your files, breaks them into pieces it understands, and reports problems it can prove or strongly suspect from the text alone: a bare except:, a function that has grown to 300 lines, a password committed in plain text. Nothing is executed, so there is no test data to prepare, no server to start and no risk from analysing code you do not trust.

This guide explains how a static analyser actually works, shows real findings on a small file, is honest about what the approach cannot see, and ends with what we learned about reading findings after scanning 53 open-source projects.

How a static analyser works, step by step

Different tools differ in depth, but nearly all follow the same pipeline. REPO-SIGHT's engine, a C++ program, does it like this for each file:

  1. Detect the language from the file extension, so .py goes to the Python front end and .java to the Java one.
  2. Tokenise. The lexer turns raw text into a stream of tokens: keywords, names, operators, string literals, comments. This is where # comments and // comments are told apart from code.
  3. Parse. The parser walks the tokens to find structure: where each function starts and ends, where a block opens and closes, how deeply it is nested.
  4. Measure. From that structure it counts lines, functions, decision points and nesting. See cyclomatic complexity and nesting depth.
  5. Apply rules. Each rule looks for one pattern, such as a call to eval(...) or an empty catch block, and records a finding with the file, line and a message.
  6. Score and report. The measurements are combined into a health score, and the findings are ranked so the important ones come first.

Because the engine reads tokens rather than building a complete compiler-grade syntax tree, it is fast and forgiving: it can analyse a file that does not compile, and a malformed file does not crash it. The trade-off is precision. A token-level rule can be fooled by unusual formatting, and the numbers are best treated as a reliable ranking of where to look rather than an audit.

A small example with real output

Here is a short Python file with four risky patterns and one stray comment in it. We ran it through REPO-SIGHT exactly as shown:

import os, subprocess, pickle

API_KEY = "sk_live_51HxQ2eLkd93jfPzR8vTn40aB"

def run_expression(user_input):
    return eval(user_input)

def ping(host):
    os.system("ping -c 1 " + host)

def load_session(f):
    return pickle.load(f)

# TODO fix this later
def x():
    pass

The engine reports five findings: py-sec-hardcoded-secret on the API_KEY line, py-sec-eval-exec on the eval, py-sec-os-system on the shell call, py-sec-pickle-load on the unpickling, and py-todo-without-ticket on the comment. Every finding names the exact line and says why it matters; for instance the eval message explains that it executes a string as code, so any part of that string built from untrusted input is a way in.

Notice what the tool did not say. It did not claim the code is exploitable, because it cannot know whether user_input ever comes from an attacker. It flagged the pattern and asked a human to check the data flow. That is the honest shape of static analysis: it narrows a large codebase down to the handful of lines worth a person's attention.

What static analysis is good at

  • Patterns that are wrong almost everywhere. Mutable default arguments, empty catch blocks, raw new/delete, hard-coded credentials.
  • Measurable structure. Function length, nesting depth, complexity and comment density are facts about the text, so they can be computed exactly and compared over time.
  • Whole-codebase consistency. A reviewer reading one pull request cannot see that the same unsafe call appears in 40 other files. A tool can.
  • Safety. It never runs the code, so scanning an unfamiliar repository cannot trigger anything inside it.

What it cannot do

  • It cannot see runtime behaviour. A static analyser does not know what values flow in, how the program behaves under load, or whether a race condition occurs. That is the job of testing and dynamic analysis.
  • It cannot judge intent. It cannot tell you that the function does the wrong thing, only that it is built in a risky or hard-to-maintain way.
  • It produces false positives. A rule that matches a pattern will sometimes match harmless code, such as a bare except: that cleans up and re-raises. This is normal, and it is why findings carry a confidence level.
  • It misses what has no pattern. A clean report does not mean correct code. It means none of the checks the tool knows about fired.

What 53 real projects taught us about reading findings

We scanned 53 well-regarded open-source projects, which produced 32,174 findings. The most useful lesson was about where the findings are: about 58% (18,568) sit in tests, documentation, examples, benchmarks or bundled third-party code rather than in the code that ships. For security findings the share was higher, 86% of 1,258. The full breakdown is in where static analysis findings actually live.

The practical rule is to check the path before the severity. A scary-looking finding in a test fixture is a different problem from the same finding in a request handler. A good tool sorts for you; a flat list of thousands of warnings teaches people to ignore the tool.

Static analysis, linting and code review

A linter is a static analyser focused on style and simple mistakes. A broader static analysis tool adds metrics, security patterns and project-level views. A human code review catches design and intent problems no tool can, but is slow and inconsistent at checking every line for the same mechanical issues. They complement each other: let the tool handle the repeatable checks so reviewers can spend their attention on the questions only people can answer.

Frequently asked questions

Is static analysis the same as a linter?

A linter is one kind of static analysis. Static analysis as a whole also covers complexity metrics, security patterns, duplication and project-level reporting.

Does it need my code to compile?

Not for a token-based engine like REPO-SIGHT's. It reads the source text directly, so it works on code that is mid-edit or missing dependencies. Tools that build a full compiler model usually need the project to build.

Will it find all my bugs?

No. It finds the bugs that have a recognisable shape. Use it alongside tests and review, not instead of them.

Is it safe to scan code I do not trust?

Yes, because the code is only read, never run. REPO-SIGHT does not execute a repository's code, tests or build scripts.
