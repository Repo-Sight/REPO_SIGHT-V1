How to improve C++ code quality

← Back to Learn

C++ gives you enough rope to write extremely fast code and enough rope to leak memory doing it. Most of the patterns worth fixing are about ownership, error handling and a handful of old C habits that modern C++ has better replacements for. This guide covers them with before-and-after code. Every example was run through REPO-SIGHT: the "before" version triggers the named rule and the "after" version comes back clean. We also use numbers from scanning 14 widely used C++ projects, so you can judge which patterns deserve attention first.

Part 1: Ownership and error handling

Raw new/delete

Manual new/delete pairs are the single most common source of leaks and double-frees in C++: every path through the function, including early returns and thrown exceptions, has to reach the matching delete, and it is easy to miss one. Rule: cpp-raw-new-delete.

Before: leaks if validate() throws

Widget* w = new Widget();
w->validate();
w->run();
delete w;

After: freed automatically on every path

auto w = std::make_unique<Widget>();
w->validate();
w->run();

This is one of the two most frequent C++ findings in our data: 2,052 hits across the 14 C++ projects, 62% of them in tests, examples and other non-production paths. It is rated medium confidence, because there are legitimate uses such as placement new or interfacing with a C library that wants to own the pointer. Read each hit; most can become std::make_unique or std::make_shared.

Empty catch-all catch(...)

An empty ellipsis catch block swallows every exception, including ones the code has no idea how to recover from, and discards the information about what went wrong. Rule: cpp-catch-all-ellipsis.

Before: silent failure

try {
    process(request);
} catch (...) {
}

After: specific, logged

try {
    process(request);
} catch (const std::exception& e) {
    log_error(e.what());
}

We checked the boundary: a catch (...) that does some cleanup and then rethrows with throw; is not flagged. That pattern is legitimate. Only the empty block is.

using namespace std; in a header

Inside a .cpp file, this is a matter of taste. Inside a header, it pollutes the global namespace of every translation unit that includes that header, which can cause subtle name collisions in files that never intended to opt in. Rule: cpp-using-namespace-std-header.

Before: widget.h

#include <string>
using namespace std;

string describe(int id);

After: widget.h

#include <string>

std::string describe(int id);

Magic numbers in conditions

A bare literal in a comparison forces the reader to guess what it means and makes the value harder to find and change consistently later. Rule: cpp-magic-number-literal.

Before

if (retries > 3) {
    giveUp();
}

After

constexpr int kMaxRetries = 3;
if (retries > kMaxRetries) {
    giveUp();
}

This is the single most frequent C++ finding: 2,175 hits across the 14 C++ projects we scanned. It is also the lowest-rated, at low severity and low confidence, because many literals are perfectly clear in context. Treat it as housekeeping, not a defect.

Part 2: Old C habits with modern replacements

These rules flag calls that are dangerous when input is attacker-controlled. A finding is a prompt to check, not proof of a vulnerability, but the replacements are usually cleaner anyway.

Unbounded buffer functions

strcpy, sprintf and friends do not check that the result fits in the destination, so a long input overruns the buffer. Rule: cpp-sec-unsafe-buffer-fn.

Before

void copy_name(char* dst, const char* src) {
    strcpy(dst, src);
}

void print_label(const std::string& name) {
    char buf[32];
    sprintf(buf, "item-%s", name.c_str());
    puts(buf);
}

After

std::string copy_name(const std::string& src) {
    return src;
}

void print_label(const std::string& name) {
    char buf[32];
    std::snprintf(buf, sizeof buf, "item-%s", name.c_str());
    std::puts(buf);
}

The best fix is to stop using character arrays: std::string grows to fit. Where you must keep a fixed buffer, snprintf takes the size and truncates instead of overflowing.

Running shell commands

system() and popen() hand a string to the shell. If any part of it comes from a user, they can append their own command. Rules: cpp-sec-system-call, cpp-sec-popen-call.

Before

void run(const char* file) {
    std::string cmd =
        std::string("cat ") + file;
    system(cmd.c_str());
}

After

void show(const std::string& file) {
    std::ifstream in(file);
    std::cout << in.rdbuf();
}

If you genuinely need another program, use the exec family with an argument array and validate the input, so nothing is parsed by a shell.

rand() for anything that matters

rand() is predictable and poorly distributed. It is fine for a visual effect and wrong for tokens, keys or anything an attacker might guess. Rule: cpp-sec-weak-random.

Before

int roll() {
    return rand() % 6;
}

After

int roll() {
    static std::mt19937 gen{std::random_device{}()};
    std::uniform_int_distribution<int> dist(1, 6);
    return dist(gen);
}

The <random> version also removes the bias that % 6 introduces. For security-sensitive randomness, such as session tokens, use the operating system's secure source or a vetted crypto library rather than mt19937, which is not designed to resist prediction.

Part 3: Structure

Two structural rules apply in every language: functions over 100 lines (cpp-long-function) and blocks nested more than 6 levels deep (cpp-deep-nesting), plus a flag for functions with cyclomatic complexity above 10 (cpp-complex-function).

How worried should you be? Across 14 C++ projects and 19,876 functions, the median function was just 6 lines long. Only 240 (1.2%) were over 100 lines and 461 (2.3%) were above complexity 10, and 64% of the long ones sat in tests, benchmarks or examples, where test frameworks like Catch2 and doctest encourage long blocks of assertions. The full analysis is in long and complex functions in 14 C++ projects. If your code has many long functions in production paths, that is well outside the norm and worth attention.

The fix is the same as in any language: split a function that does two jobs, and flatten nesting with early returns. See maximum nesting depth, explained.

What to fix first

  1. Unbounded buffer functions and system() calls on input you do not control.
  2. Empty catch (...) blocks, and raw new in code that can throw.
  3. using namespace std; in headers, which is a one-line fix with a wide effect.
  4. Magic numbers and long functions, gradually, in code you are touching anyway.

Remember where findings cluster: 44% of the 5,503 C++ findings in our scan were outside production code. Check the path before the number. See where static analysis findings actually live.

Frequently asked questions

Does REPO-SIGHT replace clang-tidy or cppcheck?

No. Those tools build a deeper model of the program, such as types and lifetimes. REPO-SIGHT reads tokens, so it is faster and works on code that does not build, but it catches fewer subtle defects. They complement each other.

Does it need a build system or compile commands?

No. It reads the source files directly, so it works without CMake, include paths or a successful compile.
