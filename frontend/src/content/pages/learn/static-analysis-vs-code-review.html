Static analysis vs. code review

← Back to Learn

Both are trying to catch problems before they ship, and they are good at catching different problems for a simple reason: a human understands intent, and a tool does not get tired. This guide shows what each one found in the same small pieces of code, summarises what is known about how reviewer attention fades, explains the part tools get wrong, and ends with a workflow that uses both, including what to do when you are working alone and there is nobody to review your pull request.

An experiment: four small files, two kinds of reviewer

We wrote four short files, one each in Python, Java, C++ and JavaScript, containing the sort of mistakes that turn up in real pull requests, and ran them through REPO-SIGHT. This is what the analyser reported (October 2026 build):

  • Python: a wildcard import (py-wildcard-import, line 1), a mutable default argument (py-mutable-default-arg, line 3) and a bare except: (py-bare-except, line 6).
  • Java: a public field (java-public-field, line 2) and an empty catch block (java-empty-catch-block, line 6).
  • C++: three raw new or delete uses (cpp-raw-new-delete, lines 4, 5 and 7) and an unsafe strcpy call, reported as a security warning (cpp-sec-unsafe-buffer-fn, line 6).
  • JavaScript: var instead of let or const, a loose == comparison, an empty catch block, and a call to eval (js-sec-eval, line 6).

Every one of those is a pattern a reviewer could spot, and every one is the kind of thing a reviewer skims past at the end of a long queue. The tool found all of them in well under a second and would find them again on the next file.

Now the other half. The Python file looks like this:

def load(path, cache={}):
    try:
        data = open(path).read()
    except:
        pass
    cache[path] = data
    return data

The analyser flagged the bare except and the mutable default, but it did not report the real bug: if the file cannot be opened, the exception is swallowed and data is never assigned. We ran it with a missing path and it crashed with UnboundLocalError: cannot access local variable 'data' where it is not associated with a value. A human reading the function sees the connection immediately, because it requires reading the code as a story: “if this fails silently, what is on the next line?” A pattern rule has no way to ask that question. That small gap is the whole case for keeping both.

What a human reviewer catches that a tool cannot

  • Whether the change solves the right problem. A rule cannot tell that a ticket asked for one thing and the code does another.
  • Design fit. Whether the abstraction will hold when the next requirement arrives, or whether it duplicates something that already exists elsewhere in the system.
  • Naming and clarity. Whether a name tells the truth about what a function does.
  • Logic that is wrong but well-formed. An off-by-one error, a flipped condition or a missing authorisation check is syntactically perfect, so no structural rule sees it.
  • Missing tests and missing cases. A reviewer can notice what is absent. A tool only analyses what is present.

What a tool catches that a reviewer often misses

A nesting depth of 9 on line 340 of a 400-line diff. A cyclomatic complexity that has crept up across a dozen small commits, none of which looked alarming alone. An empty catch that compiles and does not stand out on screen. A hardcoded token pasted into a config file. A reviewer needs to notice each of these on a given afternoon. A rule only needs to be written once.

Review attention fades, and there is data on it

The most cited study is a SmartBear analysis of code reviews at Cisco, covering about 2,500 reviews and 3.2 million lines of code. Its main findings, summarised in our words: reviews of fewer than roughly 200 to 400 lines found far more defects per line than larger ones, reviewers who moved faster than about 500 lines an hour found noticeably fewer, and effectiveness dropped when a single session ran past 60 to 90 minutes. The study also found that when authors annotated their own changes before review, results became more consistent. It came from one company and one tool, so treat the exact figures as a guide rather than a law. The direction, though, matches common experience: the sixth pull request of the day gets less scrutiny than the first.

That is the practical argument for automation. A tool has no queue and no afternoon slump. It spends the same attention on the last file as on the first, so the reviewer’s limited attention can go to what only a person can judge.

Where tools go wrong

Static analysis is not free of cost. It produces false positives and sheer volume, and a person has to decide what matters. In our scan of 53 open-source projects, the tool produced 32,174 findings, and about 58% of them were in tests, documentation, examples, benchmarks or bundled third-party code rather than shipping code. For security findings the share outside production code was 86%, and the largest single group, py-sec-hardcoded-secret, was mostly placeholder passwords in test files. A pattern matcher cannot tell a placeholder from a real credential, and a human can in a second. The full breakdown is in where static analysis findings actually live. In other words, the tool narrows the search, and the reviewer still makes the call.

A workflow that uses both

  1. Run the scan before asking for review. Fix what is plainly mechanical: the empty catch, the wildcard import, the leftover eval.
  2. Keep the change small. The Cisco data supports splitting work so that a reviewer sees a few hundred lines at a time.
  3. Tell the reviewer what you already checked. A line such as “scanned, no findings above info, remaining nesting warning is in generated code” saves them from re-checking it.
  4. Ask the reviewer the question only a person can answer. “Does this approach fit how we handle retries?” is a better request than “please look it over.”
  5. Rescan after the review. Compare the new result with the previous one to confirm the review round did not make the structure worse.

If you work alone

A team has a second pair of eyes by default, because someone has to approve the pull request. A solo developer, an indie hacker or a student does not. A structural scan is not a substitute for a reviewer’s judgement, but it is the closest thing to a second opinion when there is nobody to open a pull request against. Pair it with three habits that cost nothing: read your own diff in the pull-request view instead of your editor, since the different layout makes problems visible; leave the change for a day before merging when you can; and write a one-paragraph description of what the change is meant to do, then check that the code does exactly that, which is the step the UnboundLocalError above would have failed.

Frequently asked questions

Can static analysis replace code review?

No. It checks structure and known risky patterns. It cannot judge intent, design or correctness of business logic, which is most of what a review is for.

Should I fix every finding before requesting a review?

Fix the warnings that apply to production code and note the ones you are deliberately leaving. Not every finding deserves action, and a reviewer would rather see a short, honest list than a perfect score.

Does automation make reviewers lazy?

It can if a clean scan is treated as approval. A clean scan means none of the known patterns fired, nothing more.
