Static analysis vs. dynamic analysis

← Back to Learn

These are the two fundamentally different ways to find problems in a codebase. One reads the code. The other runs it. Most real engineering workflows use both, because each is blind to exactly the kind of problem the other catches. This guide defines each approach, then runs the same small C++ and Python programs through both so you can see the difference in actual output, and finishes with a practical order for using them together.

What static analysis does

Static analysis examines source code without executing it. A tool tokenizes and parses the text, then checks it against rules and metrics: is this function too long, is this catch block empty, how many independent paths run through this branch. There is no build step, no test harness and no runtime environment. That is also why it is fast. On our test run, REPO-SIGHT’s engine analysed the Flask web framework (83 files, about 14,000 lines of code) in roughly 0.05 seconds, plus whatever time it takes to download the repository, because it never compiles or executes any of the code it reads.

What dynamic analysis does

Dynamic analysis runs the program and observes what actually happens. Unit tests are the most familiar form. Others include memory checkers such as AddressSanitizer and Valgrind, profilers that watch real CPU and memory use, and fuzzers that send thousands of malformed inputs to see what breaks. Dynamic analysis can only report on the paths that were actually exercised during the run. It has no opinion about code that was never called.

Why neither can be complete

There is a theoretical reason the two approaches overlap rather than one replacing the other. Rice’s theorem, a result from computability theory, says no algorithm can decide every non-trivial behavioural property of arbitrary programs, such as “does this ever crash.” A static tool that tries to answer such questions must therefore approximate, and approximation means false alarms, missed problems or both. Tools that stay close to the text of the code, which is what REPO-SIGHT does, avoid the problem by not claiming to know what the program will do. They report facts about the source (this function has 14 branches) and known risky patterns (this call has no bounds check). Dynamic analysis avoids the problem differently, by observing real behaviour, but only for the inputs it was given.

The same code, analysed both ways

We wrote a small C++ file that allocates a 16-byte buffer and copies a command-line argument into it with strcpy, then compiled it with AddressSanitizer and ran it twice.

Buf* b = new Buf();
b->p = new char[16];
strcpy(b->p, src);
delete b;
  • Static result. REPO-SIGHT reported the strcpy on line 6 as a security warning (cpp-sec-unsafe-buffer-fn) and the manual allocation as three cpp-raw-new-delete notes. It reported these without being given any input, because the risk is in the code, not in a particular run.
  • Dynamic result with a short input. Running with the two-character argument hi produced no overflow. AddressSanitizer did report something the static pass had only hinted at: LeakSanitizer: detected memory leaks, with a direct leak of 16 bytes. The code deletes the struct but never the buffer inside it.
  • Dynamic result with a long input. Running with a 32-character argument produced AddressSanitizer: heap-buffer-overflow inside strcpy.

So the same program gave three different answers depending on how it was examined, and each answer was true. The static tool warned about the overflow before anything ran, and it worked for every input. The dynamic tool proved the overflow was reachable and found a leak, but only when the input made it happen.

Then we reversed it with a Python function that swallows an exception:

def load(path, cache={}):
    try:
        data = open(path).read()
    except:
        pass
    cache[path] = data
    return data

The analyser flagged the bare except and the mutable default argument. It did not report the actual failure. Running the function with a missing file ended with UnboundLocalError: cannot access local variable 'data' where it is not associated with a value. The test found a real crash that the static check could only hint at, because it required running the failure path. Each approach found something the other missed, which is the point.

What each one misses

  • Static analysis cannot tell you whether the output is correct. It can tell you a function has 8 branches and no comments. It cannot tell you the function computes the right answer. That requires running it against known inputs.
  • Dynamic analysis cannot see code it never touches. A suite with 60% coverage says nothing about the other 40%. A race condition that depends on timing will not show up if the test that would trigger it never ran.
  • Static analysis finds structural rot early; dynamic analysis finds behavioural bugs late. A cyclomatic complexity of 30 is visible the moment the function is written. The bug it eventually causes might not surface until a specific input reaches production months later.
  • Dynamic tools cost more to run. They need a working build, a runtime and usually a test harness. Sanitizers slow programs down and fuzzers can run for hours.

Static findings need triage, and so do dynamic ones

A fair comparison includes the cost side. Static tools produce volume: our scan of 53 open-source projects produced 32,174 findings, of which about 58% were in tests, documentation, examples or bundled code. That article explains how to sort them. Dynamic tools have their own noise, such as flaky tests that fail one run in fifty, or sanitizer reports in third-party code you cannot change. Neither kind of output can be trusted blindly.

A sensible order of use

  1. While writing: static checks in the editor or a quick scan. Instant, no build.
  2. Before opening a pull request: a full static scan to clear the mechanical issues, then the unit tests.
  3. In continuous integration: the complete test suite, plus sanitizers on the build types that support them.
  4. Before release or for risky parsing code: fuzzing and soak tests, where inputs you did not think of are the whole point.
  5. In production: monitoring, which is dynamic analysis of real traffic.

Static analysis comes first because it is cheap and needs nothing to exist. Dynamic analysis comes later because it needs a working program, and it is where correctness is actually established.

Frequently asked questions

Which is better, static or dynamic analysis?

Neither. They find different problems, and a codebase can pass one and fail the other. We showed a case above in each direction.

Is a unit test dynamic analysis?

Yes. Any technique that runs the code and observes behaviour is dynamic, and tests are the most common example.

Can static analysis find memory leaks?

Some tools can reason about ownership, but simple pattern-based tools cannot be sure. In our example the static pass flagged the raw allocations as a smell, and the leak itself was confirmed only when the program ran under a sanitizer.
