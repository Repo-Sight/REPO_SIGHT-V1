What is maximum nesting depth?

← Back to Learn

Nesting depth counts how many blocks are stacked inside one another at a single point in the code. An if inside a for inside a function is three levels deep. Maximum nesting depth is the deepest point anywhere in a file or project. It is one of the cheapest metrics to compute and one of the most useful to read, because it points at exactly the code that is hardest to hold in your head. This guide explains how REPO-SIGHT counts it, shows tested before-and-after examples with the real numbers, and covers the cases where a high value is not a problem.

How REPO-SIGHT counts depth

Counting conventions differ between tools, and the difference matters when you compare numbers. REPO-SIGHT counts every enclosing block, including the function itself and any class or namespace around it. We checked this by running small files through the analyser (October 2026 build):

  • Python: a class containing a method containing one if reports a depth of 3.
  • Java: the same shape, a class, a method and one if, also reports 3.
  • C++: a namespace, a class, a member function and one if reports 4.
  • JavaScript: a function containing a callback containing another callback containing an if reports 4.

So a depth of 3 in a Java file means a single if in an ordinary method, not three nested conditions. Keep that in mind when you read the number: in class-based languages two levels are already spent before any logic begins.

Why depth matters more than raw branch count

Each level of nesting is one more condition the reader has to keep active while reading the innermost line: “we are inside this if, which is inside this loop, which only runs if the earlier check passed.” Psychology has long cited George Miller’s 1956 figure of about seven items for short-term memory; later work, notably by Nelson Cowan, argues the real limit is closer to four chunks. Either way, the limit is small. Past four or five levels most readers stop tracking the state and scroll back up to rebuild it, which is where misreadings and wrong edits come from.

Depth also measures something that cyclomatic complexity does not. Complexity counts independent paths through a function. Depth counts how those paths are arranged. Two functions can have identical complexity and very different readability, and the next example shows it.

A tested before and after

Reports nesting depth 5

def handle_order(order):
    if order is not None:
        if order.items:
            for item in order.items:
                if item.in_stock:
                    ship(item)

Reports nesting depth 3, guard clauses

def handle_order(order):
    if order is None or not order.items:
        return
    for item in order.items:
        if not item.in_stock:
            continue
        ship(item)

Counting the function body as level 1, the left version stacks four more levels on top and reports 5. The right version reports 3. Every condition is still checked and the behaviour is identical. What changed is that the failure cases now exit at the top instead of wrapping everything that follows.

Two details from the actual output are worth noticing. First, the nesting component of the health score moved from 60 to 100, because the score treats a depth of 3 as fully good and a depth of 8 as fully bad, and scales linearly between them: (8 − 5) ÷ 5 = 0.6. Second, cyclomatic complexity was 5 for both versions. Flattening the code removed no decision points. It only made them easier to see, which is exactly the gap between the two metrics.

What a flagged file looks like

REPO-SIGHT raises a finding once a file passes a nesting depth of 6 (cpp-deep-nesting, py-deep-nesting, java-deep-nesting, ts-deep-nesting, js-deep-nesting and csharp-deep-nesting; the threshold is the same across all six languages). We tested the boundary: a function with five nested if statements reports 6 and is not flagged, and one with six reports 7 and is. Here is a function that crosses it:

def reconcile(accounts, ledger):
    for acct in accounts:
        if acct.active:
            for entry in ledger.get(acct.id, []):
                if entry.pending:
                    for line in entry.lines:
                        if line.amount > 0:
                            try:
                                post(line)
                            except ValueError:
                                log(line)

The analyser reports a depth of 8, a nesting score of 0 and one finding, py-deep-nesting, with the message “File reaches nesting depth 8 — consider extracting helper functions.” The severity is info, not a warning, and the finding is attached to the file rather than a single line. That is a deliberate choice: depth is a readability signal, not a defect, and the rule is meant to start a conversation about the structure rather than demand a fix.

Four ways to bring depth down

1. Guard clauses

Return or continue early on the failure case instead of wrapping the success case in another if. This is the fix shown above, and it is usually the cheapest because it changes no logic.

2. Extract the inner block

Move the innermost loop into a function with a name that says what it does. In the reconcile example, the inner loop becomes post_pending_lines(entry). The nesting does not disappear from the project, but each function now reads on one screen and the name carries the meaning the indentation was hiding.

3. Invert the condition

Checking for the case you want to reject and leaving immediately is often clearer than checking for the case you want and nesting the rest under it. If you find yourself writing a long if body with a short else that only returns, flip them.

4. Flatten callbacks with async and await

In JavaScript and TypeScript, depth often comes from nested callbacks rather than from branching. We tested a three-step lookup written with callbacks and error checks at each level. It reports a nesting depth of 4 and a cyclomatic complexity of 4. The same logic with async and await reports a depth of 1 and a complexity of 1, in five lines instead of twelve. Errors propagate through try and catch or the rejected promise, so the repeated if (err) checks are no longer needed.

What counts as nesting and what does not

A flat chain of alternatives is not nesting. We tested a Python function with an if, four elif branches and an else. It reports a depth of 2 (the function and the chain) while its complexity is 6. Six outcomes, read top to bottom, do not require the reader to remember anything from the line above. This is why a long, regular elif ladder or switch is usually fine on this metric even when it is flagged by others.

What the numbers look like in real projects

Our October 2026 scan of 53 well-regarded open-source projects shows that deep nesting is common even in respected code. The maximum nesting depth was 7 or higher in 51 of the 53 projects, and the median across all projects was 10. The lowest was 6. The highest, in the Fastify project, was 41. Those figures are a project-wide maximum, meaning the single deepest block anywhere in the repository, including tests, examples and benchmarks. A project maximum is therefore almost always an outlier, and it is why nesting carries only 10% of the health score. The useful question is not “what is the maximum” but “which file holds it, and is that production code?” The article on where findings live explains why that distinction changes what you fix first. When high nesting is acceptable

  • Generated code. Parsers, protocol buffers and template output are not written to be read. Exclude them.
  • Table-driven or state-machine code. Where each level corresponds to a genuine state, restructuring can scatter the logic and make it harder to follow.
  • Test code. Frameworks that express tests as nested callbacks or describe blocks inflate depth without making the production code harder to read.

Frequently asked questions

What is a good maximum nesting depth?

Under REPO-SIGHT’s counting, 3 or less earns full marks in the score and 8 or more earns zero. A practical aim for new functions is to stay at or below 4, remembering that the function itself, and any class around it, uses one or two levels already.

Does else if add depth?

No. An else if or elif continues the same chain, as the tested example above shows.

Can I compare depth across languages?

Roughly. The rule and the score use the same thresholds in all six supported languages, but class-based languages spend levels on class and namespace blocks and JavaScript spends them on callbacks. Compare a project with others written in the same language, or with its own earlier scans.
