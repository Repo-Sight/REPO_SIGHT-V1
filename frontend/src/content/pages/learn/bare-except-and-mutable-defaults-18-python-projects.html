Bare except and mutable defaults in 18 Python projects

← Back to Learn

Bare except:, mutable default arguments and wildcard imports are three of the most quoted Python pitfalls. We scanned 18 well-known Python projects — 1,892,200 lines of code — to see how often each really appears. In total there are 75 bare excepts, 60 mutable-default findings and 112 wildcard imports. That is about 0.13 findings per 1,000 lines, and the raw count overstates the problem once you read the code around them.

How we measured

The 18 projects are listed, with the commit scanned, in the open data file. We counted findings from REPO-SIGHT’s py-bare-except, py-mutable-default-arg and py-wildcard-import rules, then opened the code at every bare except and at the library-code mutable defaults to see what it did. A fourth rule, mutable class attributes, fired 1,988 times, more than these three combined, so we left it out. 4 projects have none of the three: click, jinja, requests and pytest.

Bare except: 75 findings, 6 projects

Only 6 of 18 projects contain a bare except at all, and one of them, SQLAlchemy, accounts for 49 of the 75. The rest are tornado (9), black (9), rich (6), scrapy (1) and flask (1).

A bare except catches everything, including KeyboardInterrupt and SystemExit. That is dangerous when the handler hides the error, and fine when it cleans up and passes the error on. This is how the 75 divide:

  • Re-raises: 29. The handler does some cleanup and raises again, as in the first example below. 23 are in library code and 6 in tests. This is a legitimate pattern, and the main reason the rule alone overstates the problem.
  • Swallows with pass: 20. 17 are in tests or test-support code. 3 are in library code: two in SQLAlchemy’s orm/loading.py and one in dialects/oracle/provision.py.
  • Handles the error: 14. The handler returns a fallback value or records the failure, 7 in library code and 7 in tests.
  • Test fixtures: 9. Every one of black’s 9 hits is in tests/data/cases, which holds sample source files for the formatter to reformat. The bare excepts are the test input, not black’s own code.
  • Logs: 3. The handler logs the exception.

Re-raises — usually fine

try:
    do_work()
except:
    cleanup()
    raise

Swallows — worth fixing

try:
    do_work()
except:
    pass

Out of 75 findings, only the 3 library swallows and perhaps a few of the 7 library handlers merit a second look. That is the real size of the problem in this data set.

Mutable defaults: 60 findings, 8 projects

The classic bug is a default such as items=[], which is created once and shared by every call. We found 60 findings at 49 distinct function definitions in 8 projects. 37 of the 49 are in tests or test-support code. Black has 17 findings, celery 13, django 9 and SQLAlchemy 8.

In the library cases we checked, the defaults were not mutated. Tornado’s ax_attrs default is rebound with set(ax_attrs) before use. Black’s Node.__init__ takes a copy with fixers_applied[:]. SQLAlchemy’s inspect_formatargspec replaces its {} defaults with kwonlydefaults or {}. FastAPI marks its own case with an explicit # noqa: B006, a sign the maintainers know about the pattern and chose it. The pattern is still worth avoiding, because the next person to edit the function may not know any of this.

Shared between calls

def add_item(item, items=[]):
    items.append(item)
    return items

One list per call

def add_item(item, items=None):
    items = [] if items is None else items
    items.append(item)
    return items

Wildcard imports: 112 findings, 8 projects

74 of the 112 wildcard imports (66%) are in __init__.py files, where from .module import * is a common way to re-export a package’s public names. Django has 36 of them, httpx 16, SQLAlchemy 15 and pydantic 10. Another 32 are in tests, and 6 are elsewhere: five in attrs’ re-export modules such as attrs/validators.py and one in Pillow’s build backend.

Wildcard imports make it harder to see where a name comes from, so they are a poor habit in application code. In a package’s __init__.py they are usually deliberate.

What to take from this

  • Read the handler, not just the rule. Half of the bare excepts here either re-raise or sit in tests and fixtures.
  • Mature projects still have a few. Even in code with heavy review, a small number of swallowed exceptions exist. They are the ones to clean up first.
  • Treat the count as a prompt. A rule that fires hundreds of times is telling you where to look, not how bad things are.

Frequently asked questions

Is a bare except ever correct?

It is acceptable when the handler cleans up and re-raises, which is the most common use in this data set. It is a bug when it silently discards the error. Catching Exception is usually the better default, because it leaves KeyboardInterrupt and SystemExit alone.

Why does REPO-SIGHT report the re-raising ones too?

The rule flags the syntax, and the report shows the code so you can judge. See how to improve Python code quality for before-and-after fixes.
