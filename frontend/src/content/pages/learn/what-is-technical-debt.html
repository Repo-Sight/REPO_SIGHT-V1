What is technical debt?

← Back to Learn

Technical debt is the future cost of choosing a quick or convenient solution now instead of a better one. Like financial debt, it lets you move faster today and charges interest later: every change to the affected code takes longer, breaks more often and is harder to explain to a new teammate. This guide explains where the idea comes from, the different kinds of debt, which parts of it a tool can actually measure, and what we saw when we counted one visible symptom, TODO comments, across 53 open-source projects.

Where the metaphor comes from

Ward Cunningham, one of the authors of the Agile Manifesto, coined the term in the early 1990s. His point was subtle and is often lost: shipping code that reflects your current, incomplete understanding of a problem is fine, provided you go back and fix it as you learn more. The debt becomes harmful when the repayment never happens and the shortcuts pile up.

The word has since stretched to cover almost any code people dislike, which makes it less useful. A cleaner definition is the one we use here: debt is a known gap between how the code is and how it needs to be for the next change to be cheap and safe.

Not all debt is the same

Martin Fowler's well-known quadrant sorts debt along two lines: was it deliberate or accidental, and was it prudent or reckless?

  • Deliberate and prudent. "We will ship now and refactor after launch." A conscious trade with a plan to repay it. This is the healthy kind.
  • Deliberate and reckless. "We have no time for design." The team knows better and does it anyway.
  • Accidental and prudent. "Now we know how we should have built it." Learning only arrives after the code exists. Unavoidable, and worth fixing when you notice.
  • Accidental and reckless. The team did not know the basics and built something fragile without realising it.

A tool cannot tell you which quadrant a piece of debt belongs to, because that depends on why the code was written. It can show you where the code is hard to change, and you can supply the reasons.

What you can measure and what you cannot

Technical debt is partly visible in the source text and partly not. Be clear about which is which, because a score that implies it captures everything would mislead you.

Visible in the code, and measurable by static analysis:

  • Long functions. REPO-SIGHT flags functions over 100 lines. See long and complex functions in 14 C++ projects.
  • High cyclomatic complexity. Functions above 10 are flagged individually.
  • Deep nesting. Blocks nested more than 6 levels deep are flagged.
  • Unticketed TODO and FIXME comments. A note that says "fix this later" with nothing tracking it is debt that nobody owns.
  • Known-risky patterns. Empty catch blocks, mutable default arguments, raw new/delete: shortcuts that tend to turn into bugs.
  • Thin documentation. Comment density is a rough proxy for how much of the code's intent is written down.

Not visible from the source alone:

  • Missing or weak automated tests.
  • Outdated dependencies and unpatched libraries.
  • Architectural debt: a module boundary in the wrong place, a database schema that no longer fits.
  • Knowledge debt: the one person who understands a subsystem has left.

REPO-SIGHT measures the first list and says so. It does not put a dollar figure or a "days to fix" estimate on debt, because any such number would be invented. What it gives you is a ranked list of specific places where the code is expensive to change.

A symptom we counted: TODO comments

Of all the visible signs, TODO and FIXME markers are the easiest to count and the easiest to misread, so we measured them across the 53 projects in our open data file. Together the projects hold about 4.38 million lines of code and 2,951 TODO or FIXME markers, roughly 0.67 per 1,000 lines. Several findings stand out:

  • The count is very uneven. Google Guava alone accounts for 1,663 of the 2,951, which is 56%. Take Guava out and the other 52 projects together hold 1,288.
  • 10 of the 53 projects have none at all, including Flask, Click, axios, Express and lodash.
  • Language and culture matter. The Java projects average about 1.5 markers per 1,000 lines, Python about 0.3, and the two C# projects almost none.

The full breakdown, including how marker density relates to project age, is in do older repositories carry more TODOs?. The lesson for debt is that a TODO count is a weak signal by itself. A project with none may track its debt in an issue tracker instead; a project with many may simply be honest about it. What the count can tell you is whether notes are being left behind with nobody assigned to them.

That is why REPO-SIGHT's TODO rules (py-todo-without-ticket, java-todo-without-ticket and the C++ equivalent) do not flag every TODO. They flag the ones without a ticket reference. For example:

# TODO fix this later          <- flagged
# TODO(#142): remove after migration   <- not flagged

We ran both lines through REPO-SIGHT. The first is reported; the second, which points at issue #142 or a key like PROJ-123, is not. The second form turns an anonymous wish into a tracked piece of work.

Managing debt without drowning in it

  1. Make it visible. Debt you cannot see cannot be prioritised. A scan that lists the worst functions and files gives the team a shared starting point.
  2. Rank by cost of change, not by ugliness. A tangled function nobody touches costs little. A moderately messy one that changes every week costs a lot. REPO-SIGHT's hotspot view combines complexity with how often a file changes when git history is available.
  3. Pay a little every time. Leave each file slightly better than you found it. Steady repayment beats a big rewrite that never gets approved.
  4. Attach every TODO to a ticket. It forces a decision: either it matters enough to track, or the comment should go.
  5. Re-measure. Rescan after a cleanup and compare. A before-and-after number is how you show that repayment is working.

Frequently asked questions

Is technical debt always bad?

No. Deliberate, tracked debt is a normal engineering trade-off. It is bad when it is hidden, untracked, or never repaid.

Can a tool calculate how much debt I have?

It can find and rank the places where code is long, tangled or risky. Turning that into a single money or time figure requires assumptions a tool cannot know, so treat any such number sceptically.

Does a high code health score mean no debt?

No. The score covers complexity, function length, comments, TODOs and nesting. It says nothing about tests, dependencies or architecture.
