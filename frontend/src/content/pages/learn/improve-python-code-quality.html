How to improve Python code quality

← Back to Learn

Most Python quality problems are not exotic. They are a small, repeatable set of patterns that look harmless when you write them and cause a confusing bug months later. This guide covers the ones worth fixing first, with before-and-after code for each. Every example was run through REPO-SIGHT: the "before" version triggers the named rule and the "after" version comes back clean. We also use data from scanning 18 well-known Python projects to show how common each pattern really is, so you can tell what is worth your time.

Part 1: Pitfalls that cause bugs

Bare except: blocks

A bare except: catches everything, including KeyboardInterrupt and SystemExit, which almost never should be silently swallowed. It also hides the actual error, making the real bug harder to find later. Rule: py-bare-except.

Before

try:
    result = risky_call()
except:
    result = None

After

try:
    result = risky_call()
except (ValueError, KeyError) as exc:
    log.warning("risky_call failed: %s", exc)
    result = None

How common is it? Across the 18 projects, about 1.9 million lines of code, we found 75 bare excepts, and 49 of them were in one project (SQLAlchemy). Roughly 29 of the 75 were the harmless kind that clean up and then re-raise. Fix the handlers that swallow the error; leave the ones that re-raise. The details are in bare except and mutable defaults in 18 Python projects.

Mutable default arguments

Default argument values are evaluated once, when the function is defined, not once per call. A mutable default like [] or {} is silently shared and mutated across every call that does not pass its own value, producing state that leaks between unrelated calls. Rule: py-mutable-default-arg.

Before: the list is shared across calls

def add_item(item, items=[]):
    items.append(item)
    return items

After: a fresh list every call

def add_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items

We found 60 of these across the 18 projects. This is a pattern where the bug is real even when the rule fires only occasionally, because the failure is silent: the function works the first time and misbehaves later.

Mutable class attributes

The same sharing problem, one level up: a mutable value assigned at the class level is one single object shared by every instance, not a fresh copy per instance. Rule: py-mutable-class-attribute.

Before: every instance shares one list

class Cart:
    items = []

After: initialised per instance

class Cart:
    def __init__(self):
        self.items = []

This is by far the noisiest of the four: it fired 1,988 times across the 18 projects, more than the other three combined. It is rated medium confidence for that reason. Class-level lists are sometimes deliberate constants, so read each hit rather than fixing them in bulk.

Wildcard imports

from module import * pollutes the current namespace with everything the module exports, and hides exactly where any given name came from, both for readers and for tools trying to trace where a symbol is defined. Rule: py-wildcard-import.

Before

from utils import *

After

from utils import normalize, slugify

Part 2: Security patterns to review

These rules flag calls that are dangerous if untrusted input reaches them. A finding is a prompt to check the data flow, not proof of a vulnerability. The safer replacements are almost always no harder to write.

Running strings as code or commands

eval and exec run a string as Python. os.system and subprocess with shell=True run a string through the shell. If any part of that string is built from user input, an attacker can add their own commands. Rules: py-sec-eval-exec, py-sec-os-system, py-sec-subprocess-shell-true.

Before

def run_expression(user_input):
    return eval(user_input)

def ping(host):
    os.system("ping -c 1 " + host)

def list_dir(path):
    subprocess.run("ls " + path, shell=True)

After

def run_expression(user_input):
    return ast.literal_eval(user_input)

def ping(host):
    subprocess.run(["ping", "-c", "1", host], check=True)

def list_dir(path):
    subprocess.run(["ls", path], check=True)

Passing the command as a list means the host or path is a single argument, never parsed by a shell. ast.literal_eval only accepts literals such as numbers, strings and lists, so it cannot run code.

Unsafe deserialisation

pickle.load can execute arbitrary code while reading data, and yaml.load without a safe loader can construct arbitrary Python objects. Never use either on data you did not produce yourself. Rules: py-sec-pickle-load, py-sec-yaml-unsafe-load.

Before

def load_session(f):
    return pickle.load(f)

def read_config(text):
    return yaml.load(text)

After

def load_session(f):
    return json.load(f)

def read_config(text):
    return yaml.safe_load(text)

Weak hashes and committed secrets

hashlib.md5 is broken as a security hash, and a fast hash of any kind is the wrong tool for passwords. A password should go through a deliberately slow function such as scrypt. A string literal assigned to a name like API_KEY ends up in git history forever. Rules: py-sec-weak-hash, py-sec-hardcoded-secret.

Before

API_KEY = "sk_live_51HxQ2eLk..."

def hash_password(pw):
    return hashlib.md5(pw.encode()).hexdigest()

After

API_KEY = os.environ["API_KEY"]

def hash_password(pw, salt):
    return hashlib.scrypt(
        pw.encode(), salt=salt, n=2**14, r=8, p=1
    ).hex()

Two notes. If a secret was ever committed, treat it as leaked: rotate it, because deleting the line does not remove it from history. And MD5 is acceptable for non-security uses such as a cache key; hashlib.md5(data, usedforsecurity=False) states that intent and is not flagged.

Part 3: Structure and upkeep

Deep nesting

More than 6 levels of nested blocks raises py-deep-nesting. This function reports a maximum nesting of 7:

def process(orders):
    for o in orders:
        if o.paid:
            for line in o.lines:
                if line.stock:
                    for w in line.warehouses:
                        if w.open:
                            ship(w, line)

Use an early continue and pull the inner loop into its own function:

def ship_line(line):
    for w in line.warehouses:
        if w.open:
            ship(w, line)


def process(orders):
    for o in orders:
        if not o.paid:
            continue
        for line in o.lines:
            if line.stock:
                ship_line(line)

Maximum nesting drops from 7 to 4 and the finding disappears. The number of decisions in the file is unchanged, but each function now fits in your head. More on this in maximum nesting depth, explained.

Long and complex functions

Functions over 100 lines raise py-long-function, and those with a cyclomatic complexity above 10 raise py-complex-function. The usual cure is to split a function that does two jobs, such as validating and then transforming, into two functions with clear names.

Untracked TODOs

py-todo-without-ticket flags a TODO or FIXME with no ticket reference. Add one and the finding goes away:

Before

# TODO fix this later

After

# TODO(#142): remove after migration

What to fix first

  1. Any hard-coded secret (rotate it too), then any shell, eval or unpickling of input you do not control.
  2. Bare excepts that swallow errors and mutable default arguments, because they cause silent bugs.
  3. Deeply nested or very long functions in code that changes often.
  4. Wildcard imports, untracked TODOs and mutable class attributes, in your own time.

Do not chase the raw count. In our data, 62% of Python findings were in tests, docs, examples or bundled code. Check the path before the number; see where static analysis findings actually live.

Frequently asked questions

Does REPO-SIGHT check type hints or PEP 8 style?

No. It focuses on risky patterns, security checks and structural metrics. Pair it with a formatter such as Black or Ruff for style.

Will it analyse my docstrings?

For the comment-density part of the health score, only # comments are counted. A function with a three-line docstring and one # comment reports one comment line, so well-documented Python can still score low on that component.

Check your own project

These rules are REPO-SIGHT's actual Python checks. Run it on a Python repository or use the Python code analyzer to see which of them show up in your code.
