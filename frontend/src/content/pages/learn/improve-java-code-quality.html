How to improve Java code quality

← Back to Learn

Java's quality problems tend to cluster around encapsulation, error handling and a short list of classic security mistakes. They compile cleanly and pass a quick glance, but cause real maintenance pain later. This guide covers the patterns worth fixing first, with before-and-after code. Every example was run through REPO-SIGHT: the "before" version triggers the named rule and the "after" version comes back clean, with one exception we call out. We also use data from 13 well-known Java projects, 140,090 methods in all, to show how common these problems are in respected code.

Part 1: Error handling and encapsulation

Empty catch blocks

An empty catch block compiles fine and silently discards the exception, which means a real failure produces no signal anywhere: no log line, no stack trace, nothing to search for when something downstream breaks. Rule: java-empty-catch-block. REPO-SIGHT rates it high severity with high confidence, and promotes it to the "fix now" card at the top of a report.

Before: failure vanishes silently

try {
    connection.send(payload);
} catch (IOException e) {
}

After: failure is visible

try {
    connection.send(payload);
} catch (IOException e) {
    logger.error("send failed", e);
}

If ignoring the exception is genuinely correct, say so: put a comment inside the block explaining why, or catch the narrowest type possible. An empty block with no explanation is indistinguishable from a bug.

Public fields

A public field lets any caller mutate it directly, with no chance to validate the new value or react to the change. The entire point of encapsulation is to prevent exactly this. Rule: java-public-field.

Before: anyone can set a negative balance

public class Account {
    public double balance;
}

After: validated on the way in

public class Account {
    private double balance;

    public void setBalance(double value) {
        if (value < 0) throw new IllegalArgumentException();
        this.balance = value;
    }
}

One exception is built in. A class that only holds data, with fields, constructors, toString/equals/hashCode and plain get/set/is accessors and nothing else, is treated as a deliberate DTO or POJO, and its public fields are not flagged. We checked this: a UserDto with two public fields and a getter and setter produces no finding, while the same public field on a class with real behaviour does. That keeps the rule from burying you in noise on data-transfer classes.

printStackTrace() in production paths

printStackTrace() writes straight to stderr, which is easy to lose entirely in an environment with real log aggregation. A proper logger routes the same information somewhere it can be searched later. Rule: java-printstacktrace.

Before

catch (Exception e) {
    e.printStackTrace();
}

After

catch (Exception e) {
    logger.error("operation failed", e);
}

Raw types

Using a generic class without its type parameter turns off compile-time type checking for it, so a wrong element type surfaces as a ClassCastException at runtime instead of an error at compile time. Rule: java-raw-type-usage.

Before

List items = new ArrayList();

After

List<String> items = new ArrayList<>();

Part 2: Security patterns to review

These rules flag code that is dangerous if untrusted input reaches it. A finding is a prompt to check the data flow, not proof of a vulnerability.

SQL built by string concatenation

Gluing user input into a query string is the textbook route to SQL injection. A PreparedStatement sends the query and the values separately, so the values can never change the query's structure. Rule: java-sec-sql-string-concat.

Before

Statement s = c.createStatement();
return s.executeQuery(
    "SELECT * FROM users WHERE name = '"
    + name + "'");

After

PreparedStatement s = c.prepareStatement(
    "SELECT * FROM users WHERE name = ?");
s.setString(1, name);
return s.executeQuery();

Weak hashes and ciphers

MD5 and SHA-1 are broken for collision resistance, and DES has a key far too small to be safe. Rules: java-sec-weak-hash, java-sec-weak-cipher.

Before

MessageDigest.getInstance("MD5");
Cipher.getInstance("DES");

After

MessageDigest.getInstance("SHA-256");
Cipher.getInstance("AES/GCM/NoPadding");

For storing passwords, even SHA-256 is the wrong tool because it is fast. Use a slow, salted password hash such as bcrypt, scrypt or Argon2. MD5 is still fine for a non-security checksum, which is why the weak-hash rule is rated low confidence.

Launching operating-system commands

Runtime.getRuntime().exec(...) with a single concatenated string lets user input add extra commands or arguments. Rule: java-sec-runtime-exec.

Before

Runtime.getRuntime()
    .exec("convert " + arg);

After: separate arguments

new ProcessBuilder("convert", arg).start();

This is the one exception to "the after version comes back clean". REPO-SIGHT flags any process launch for review, including new ProcessBuilder(...), because it cannot tell whether arg was validated. The fix still matters: with separate arguments, arg is one argument and cannot smuggle in a second command. The finding that remains is the reminder to confirm the value is checked.

Trust-everything certificate managers

A custom X509TrustManager whose methods do nothing disables certificate validation, which makes every HTTPS connection open to interception. Rule: java-sec-trust-manager-review, which is deliberately low confidence because many custom managers are legitimate. If the class exists only to make an SSL error go away, delete it and fix the real certificate problem instead.

Part 3: Structure

Methods over 100 lines raise java-long-method, blocks nested more than 6 deep raise java-deep-nesting, and methods above cyclomatic complexity 10 raise java-complex-function. Java is a good place to calibrate expectations, because mature projects keep these rare. Across the 13 projects we scanned, the median method was 5 lines, and only 211 of 140,090 methods (0.15%) were over 100 lines. About 984 were above complexity 10, and 86% of those were in production code, so branching is a production-code habit even when very long methods are mostly tests.

The long methods that do ship in production are a recognisable set: parsers, annotation handlers and framework internals. Retrofit's parseParameterAnnotation runs 456 lines because it has one branch per annotation type. If your long methods are not parsers or protocol handlers, they are probably doing too many jobs. What to fix first

  1. Empty catch blocks, because they hide failures and they are high-confidence.
  2. String-built SQL and OS commands on input you do not control.
  3. Weak ciphers and hashes used for security purposes.
  4. Public fields on classes with real behaviour, raw types and printStackTrace(), as you touch the code.

Java projects scored best in our data: 11 of 13 earned an A on REPO-SIGHT's code health score, partly because Javadoc and // comments count in full toward comment density. Frequently asked questions

Does REPO-SIGHT understand Spring, Lombok or annotations?

It reads Java source as tokens and does not expand annotation processors. Code generated by Lombok is not visible to it, so it analyses the source as written.

Can it replace SpotBugs or PMD?

No. Those tools work on bytecode or a full syntax tree and catch more subtle defects. REPO-SIGHT is quick, needs no build, and focuses on a ranked, plain-English list of the most important problems.
