What REPO-SIGHT checks in your C code

19 rules, tuned for C — 10 of them security-specific. Every .c file in the repo is analyzed.

Complexity & structure

Cyclomatic complexity, max nesting depth (c-deep-nesting flags files past 6 levels), c-long-function for functions over 100 lines, and c-complex-function for functions past complexity 10 — the same thresholds used in the health score.

Unsafe buffers & input

c-sec-unsafe-buffer-fn flags gets, strcpy, strcat, sprintf and vsprintf, and c-sec-unsafe-scanf flags %s and %[ conversions with no field width.

Format strings & shell commands

c-sec-format-string flags printf(msg)-style calls that use a plain variable as the format, and c-sec-system-call / c-sec-popen-call flag system() and popen() — unless the command is made only of string literals and macro constants.

Memory handling

c-malloc-unchecked catches a pointer from malloc, calloc, realloc or strdup that is dereferenced in the very next statement with no NULL check, and c-realloc-self-assign catches p = realloc(p, n), which leaks the block when the allocation fails.

Macros, temp files, crypto & secrets

c-macro-multi-statement flags function-like macros with several statements and no do { } while (0) wrapper; c-sec-insecure-temp-file flags tmpnam, tempnam and mktemp; weak rand/MD5/SHA1 use and hardcoded credentials round out 10 security checks in total.

Duplication & debt

Token-based clone detection across the whole repo, plus every TODO/FIXME counted — c-todo-without-ticket flags the ones with no ticket reference.

Warning · example finding 
char name[32];
strcpy(name, argv[1]);
printf(name);

Illustrative example. c-sec-unsafe-buffer-fn: strcpy copies until the terminating NUL without looking at the size of name, so a longer argument overwrites neighbouring memory. c-sec-format-string also fires on the last line — printf("%s", name) keeps the text out of the format.

Frequently asked questions

Which C files does it analyze?

Every .c file in the repository. Header files (.h) count as C when the repo has .c files and no C++ source files; in a repo that mixes C and C++, .h files are analyzed as C++.

Does it understand the preprocessor and macros?

Preprocessor lines are read as single directives and are not expanded, so code that only exists after macro expansion is not analyzed. #define lines themselves are checked by c-macro-multi-statement.

How is this different from clang-tidy or cppcheck?

Those tools can follow data through your code and usually need a build setup. REPO-SIGHT is token-based with no data-flow tracking, so it flags patterns for review and labels each finding with a confidence level. It runs from a GitHub URL alone and rolls the result into one project health score — a quick picture of the whole repo, not a replacement for a full toolchain.

Does REPO-SIGHT build or run my code?

No. It's static analysis only — the source is parsed, never compiled or executed.
